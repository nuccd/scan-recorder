# 扫码调优实操手册

适用版本：Android App `0.5.0`。`main` 统一维护一个「扫码记录」App，首页入口为「设置」，识别调优和诊断是常规功能，无需独立调优安装包。扫码和设置页固定竖屏。设置页另有首次默认关闭、记住选择的 [USB 扫码枪模式](windows-receiver.md)。本文用于在识别速度、超时率和错误候选之间对比参数，实验值不代表最佳配置。

## 1. 从哪里进入

打开 **扫码记录 → 右上角「设置」→ 识别调优**。扫码枪开关和识别参数在同一设置页，一并应用或取消；页面可滚动，底部操作按钮保持可见。

App 包名沿用原「扫码记录」的 `io.github.nuccd.scanrecorder`，同包名、同签名覆盖安装可保留已有批次和记录。旧的独立调优 App（`io.github.nuccd.scanrecorder.tuning`）及其数据不会被删除，也不会自动迁移到统一 App；需要的旧记录仍可在旧 App 内导出。

- **应用并返回**：保存本页参数，返回后用于扫描；重新打开 App 仍保留。
- **恢复默认参数草稿**：仅恢复本页默认值，识别参数沿用 0.4.1，默认变焦倍率为 2.3×，扫码枪模式草稿同时关闭；仍需点击「应用并返回」才生效。
- **取消并返回 / 系统返回**：放弃本页修改，保留之前已保存的配置。
- 固定竖屏不会随手机转向改变布局；系统保留状态后发生 Activity 或进程重建时，保留尚未应用的草稿。
- 主页 **复制诊断**：复制参数、设备信息和统计，不含扫码原文。
- 主页 **清零统计**：重新累计诊断，不重启相机、不删除记录。暂停后重新开始扫描也会开始新的统计会话。

建议先恢复默认参数并应用，做一组对照，再开始调整。这组对照包含新的 2.3× 默认倍率，与原始 0.4.1 新启动时的 1× 不同。

## 2. 参数说明与默认值

### 引擎、码制、分辨率与默认变焦

| 参数 | 默认值 / 可选项 | 作用与对比方法 |
| --- | --- | --- |
| 识别引擎 | 默认双引擎；可选仅 ML Kit、仅原生一维码 | 双引擎合并结果；单引擎模式用于判断哪个引擎更适合当前标签。仅 ML Kit 不运行原生解码，仅原生不运行 ML Kit。 |
| 识别码制 | 默认全部；可选仅一维条形码、仅 QR 二维码 | 限制实际尝试的格式。业务只扫条形码时，可单独比较「仅一维条形码」。它不会检查内容是否是 IMEI。 |
| 请求分析分辨率 | 默认 720p：1280×720；可选 1080p：1920×1080 | 较高分辨率可能保留更多条纹细节，也会增加计算量。相机可能选择临近尺寸，必须记录主页显示的实际尺寸。 |
| 默认变焦倍率 | 默认 2.3×；可输入 1.0–10.0 的有限小数 | App 新启动时使用的起始倍率，实际按相机支持范围裁剪。倍率滑条显示相机实际使用值。 |

主页「条形码 / 二维码」只改变白色扫码框形状；调优页「识别码制」才限制解码格式。**仅原生一维码不能与仅 QR 二维码组合**，界面会阻止应用此组合。

| 范围 | 实际格式 |
| --- | --- |
| 一维条形码（9 种） | Code 128、Code 39、Code 93、Codabar、EAN-13、EAN-8、ITF、UPC-A、UPC-E |
| 全部格式中的二维格式 | QR Code、Data Matrix、PDF417、Aztec |
| 仅 QR | 仅 QR Code，不包括其他二维格式 |

原生引擎补充上述 9 种一维码，不解 QR；ML Kit 承担二维码及其支持的一维码识别。原生处理完整分析帧，白框用于解码结果的完整边界检查，当前没有白框裁剪加速或 OCR。请求 720p / 1080p 不等于相机必然提供该尺寸。

默认变焦倍率与当前倍率分别保存和使用：App 冷启动采用已保存的默认倍率，初始为 2.3×；本次手动调节后，暂停继续和系统保留状态后的 Activity、进程重建会恢复当前倍率。固定竖屏不会因横放手机切换布局。只修改其他调优参数时保留当前倍率；修改默认变焦倍率并应用后，新倍率在返回扫码时生效。本包内已有的配置若没有默认倍率字段，补用 2.3×，其余已保存参数保留；旧独立 `.tuning` 包的配置不会自动读取。

### 稳定识别与对焦

| 参数 | 默认值 | 可输入范围 | 实际含义 |
| --- | --- | --- | --- |
| 至少一致帧数 | 3 帧 | 1–10 | 需要多少帧成功读到相同内容。空帧不计数；同一帧两个引擎读到相同内容只算一帧。 |
| 最短观察时间 | 200 ms | 0–1500 ms | 从本轮候选第一次成功识别起，至少观察多久；必须同时满足一致帧数。 |
| 漏识别容忍时间 | 150 ms | 0–1000 ms | 从首次未解码帧开始计时。短暂漏识别可保留已有证据；后续空帧不延长期限。持续成功但处理较慢的帧不会因此被当作漏识别。 |
| 证据总窗口上限 | 600 ms | 200–3000 ms | 本轮证据最多保留多久，超时重新累计。必须大于或等于最短观察时间。 |
| 点击对焦后阻帧时间 | 300 ms | 0–1000 ms | 点击对焦后，最多等待多久再允许新帧参与识别；提前完成对焦可提前结束等待。不是镜头完成对焦所需的时间。 |

例如：`A@0ms → A@80ms → 未解码@130ms → A@200ms`，默认参数可满足 3 次一致识别与至少 200ms 的观察时间。缺失帧本身不增加成功次数。

不同内容、框内多个不同内容、已解码但完整边界不在框内、相机状态改变或暂停确认等情况会重置候选。点击对焦后的自动取消时间目前固定为 3000ms，不在页面中调整。

### 原生一维码选项

这些选项只在双引擎或仅原生模式中起作用。

| 参数 | 默认值 | 含义与注意点 |
| --- | --- | --- |
| 加强搜索 `tryHarder` | 开 | 使用更充分的搜索。可关闭做速度对照，但要同时记录小码漏识别是否增加。 |
| 尝试旋转 `tryRotate` | 开 | 尝试不同方向的条码。比较关闭前后时，也要覆盖转向的标签；该选项不控制屏幕方向。 |
| 引擎尝试反色 `tryInvert` | 开 | 原生引擎提供的反色选项；不等于下面的显式反色补扫。 |
| 尝试缩小图像 `tryDownscale` | 关 | 开启原生引擎的缩图搜索。对小码的影响要实测，不能直接理解为更快。 |
| 显式反色补扫 `invertFallback` | 开 | 标准原生解码无结果时，反转灰度再尝试一次；已有结果时不执行这一遍。 |
| 原生最少扫描线数 `minLineCount` | 2 | 可输入 1–5，控制原生一维码内部的扫描线要求，与上面的「一致帧数」不同。首轮保留 2。 |

正常与反色条码混排时，不保证所有码都被检出。测试和使用时仍应一次只对准一个完整的码。

## 3. 建议怎么调

先使用原来的 3 帧 / 200ms 和 `minLineCount=2`，优先判断瓶颈在解码、细节还是对焦等待。下列每项分别与基线比较，先不要叠加。

| 顺序 | 本轮只改一项 | 重点观察 |
| --- | --- | --- |
| T00 | 保持全部默认值 | 建立成功率、耗时和错误候选的对照。 |
| T01 | 扫条形码时，码制改为「仅一维条形码」 | 限制格式后是否有收益；此组不用于评价二维码。 |
| T02 | 引擎改为「仅 ML Kit」 | 观察关闭原生后，帧耗时与当前标签成功率的变化。 |
| T03 | 引擎改为「仅原生一维码」 | 对同一条形码比较原生识别能力；不测试二维码。 |
| T04 | 仅关闭 `tryHarder` | 是否降低处理耗时，同时留意小条码超时。 |
| T05 | 仅将请求分辨率改为 1080p | 实际尺寸是否改变，小码成功率是否足以抵消新增耗时。 |
| T06 | 有明显对焦等待时，仅将阻帧 300 改为 200ms | `CAMERA_ADJUSTING` 次数、出现候选的时间和错误候选是否改善。 |
| T07 | 仅改变默认变焦倍率并应用，例如 2.3 改为 2.8× | 记录相机实际倍率、完整条码能否留在框内及候选出现时间；本组不要同时改距离或识别参数。 |

完成这些对比后，再决定是否单独试稳定帧数、观察时间、漏识别容忍等参数。降低它们可能更快出现候选，也可能增加误识别，不能只记录速度。

## 4. 每组怎样测试

1. 准备普通纸质条码、小条码、屏幕条码、QR 二维码四类样本；不支持该类型的引擎组合跳过对应样本。
2. 同一组比较使用同一台扫描手机、同一标签，保持距离、倍率、光照和持握方式一致。固定、单手、双手分别记录，避免混在一组。
3. 小条码可先沿用已经能工作的倍率；除专门比较倍率的实验外，对照时保持实际倍率不变。改变其他参数时不要同时改倍率、反光遮挡和距离。比较历史 0.4.1 时，也应先统一实际倍率。
4. 每类先做 10 次。**从完整码进入扫描框，计时到待确认窗口出现**；不包括人工核对、确认和保存的时间。
5. 5 秒仍未出现窗口，记一次超时。出现错误内容，记一次错误候选；即使很快也不算正确成功。
6. 核对后可取消录入。再次测同一码前移出框外至少 500ms，再放入；不要用持续对着同一码是否重复弹窗来判断速度。
7. 开始本组前清零统计，结束后复制诊断。记录正确成功次数、超时数、错误候选数、成功样本耗时中位数和最慢值。
8. 发现有效参数后，再单独验证多码、重复提示、取消和确认录入，以及二维码场景。

反光、手抖、条纹实际占据的像素和最近对焦距离仍会影响识别。固定状态可读，不能直接证明单手状态也达到 1–2 秒。

## 5. 诊断数据怎么看

主页每秒最多更新一次诊断，阶段计数、平均和峰值仍按每个分析帧累计。

| 字段 | 含义 |
| --- | --- |
| 实际尺寸 / `image` / `rotation` | 相机实际分析缓冲区尺寸及图像旋转角度，不是屏幕截图尺寸，也不表示 App 切换到了横屏。 |
| 帧 / `frameDecodeMs` | 本帧从开始处理到合并回调的耗时，包含所启用引擎及回调等待。 |
| 均 / `average` | 本次统计内所有分析帧的处理耗时均值。 |
| 峰 / `max` | 本次统计内单帧处理耗时最大值。 |
| `mlKitMs` | 本帧 ML Kit 任务完成的等待时间，不是纯 CPU 运算时间。 |
| `nativeMs` | 本帧原生处理耗时；执行了显式反色补扫时也包含这一遍。 |
| 引擎命中数量 | 各引擎返回结果的数量。两个引擎可能读到同一个码，不代表扫描了两台手机。 |
| `decoded` / `inWindow` / `distinctInWindow` | 有效文本解码数量、完整落在框内的数量、框内不同内容数。 |
| `totalFrames` / `sessionMs` | 统计期间的分析帧总数与时长；不是相机的原始帧率或业务录入总数。 |
| `nativeAvailable` | 原生解码当前是否可用；仅 ML Kit 或仅 QR 模式会显示原生关闭。 |

**两个引擎可能重叠运行，不能把它们的耗时相加；帧耗时也不等于一次扫码的完整识别耗时。** 选了「仅 ML Kit」后原生显示关闭，是模式设置的结果。

### 常见状态与排查方向

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| `NO_DECODE` | 本帧没有解出有效文本 | 对比引擎、倍率、清晰度、反光和分析分辨率；单纯降低一致帧数不能让未解出的码变成结果。 |
| `OUTSIDE_WINDOW` | 有结果，但完整边界没有落在框内 | 检查完整条码、四周空白及白框位置，适当退远或调倍率。 |
| `MULTIPLE_VALUES` | 框内有多个不同内容 | 对准一个码；若只有一个物理码，可比较两种单引擎模式是否给出不同文本。 |
| `WAITING_FOR_STABILITY` | 有唯一内容，仍在积累帧数和时间 | 先看是否反复漏识别，再单独比较稳定性参数。 |
| `CAMERA_ADJUSTING` | 正在调整，或该帧属于旧相机状态 | 区分刚变焦、刚点击对焦与持续等待，再考虑阻帧参数。 |
| `ALREADY_REPORTED` | 本码在本次会话已经触发 | 移出框外再测，这是重新触发规则。 |
| `REVIEW_PAUSED` | 正在确认上一条 | 确认或取消后继续。 |
| `TRANSFORM_UNAVAILABLE` | 预览与分析图坐标还未就绪 | 刚启动时短暂出现可观察；持续出现时保留诊断。 |
| `DELIVERED` | 已送到待确认流程 | 还没有保存，需用户确认。 |

## 6. 记录模板

复制下面模板，每轮保存一份；实际内容可以放到 D 盘项目的 `build/tuning/<实验编号>/`，不会进入 Git。

```text
实验编号：T00
App版本 / 源码提交：
扫描手机 / Android版本：
样本类型：普通条码 / 小条码 / 屏幕条码 / QR
持握：固定 / 单手 / 双手
光照及反光：
距离 / 倍率 / 屏幕码亮度：
默认倍率 / 相机实际倍率：
与基线相比只改了哪一项：
实际分析尺寸：
正确成功：__/10
超时（超过5秒）：__/10
错误候选：__/10
正确成功样本中位耗时：__秒
正确成功样本最慢耗时：__秒
结论：保留 / 退回 / 待复测

复制诊断：
粘贴“复制诊断”生成的完整文本报告
```

报告包含当前全部参数、设备信息、倍率、最新帧信息和累计阶段计数，不含扫码原文。切换配置会清掉旧诊断快照，开始扫描后再采集新数据。

## 7. 恢复与 Git 约定

- 参数不好用：进入「设置」，点击「恢复默认参数草稿 → 应用并返回」。这会恢复识别默认参数及 2.3× 默认倍率，同时关闭手机扫码枪模式，不删除批次和记录；取消则保留原来的配置。
- 历史对照源码提交为 `5cde343`（0.4.1）。`main` 已纳入调优功能，`codex/scan-tuning` 是此前开发该功能的分支；需要比较原始 0.4.1 时，使用该历史提交作为比较点。
- **在手机改参数不会改变 Git，也不会产生 commit。** 用上面的诊断和记录模板保存实验结果。
- 修改源码、固化有效默认参数或新增业务时，通过相关验证后再做本地 commit，说明改了什么、如何验证以及收益或退化。
- 后续分支合并和推送 GitHub 按用户明确指示执行。
- SDK 路径、Android Studio 本地配置、缓存、数据库、真实扫码内容、APK 和用户截图不提交。

## 8. 构建与交付

使用项目脚本构建统一 App，默认任务为 `:recorder:assembleBundledDebug`：

```powershell
.\scripts\build.ps1 -JdkHome '<本机JDK路径>'

# 也可显式指定同一构建任务：
.\scripts\build.ps1 -JdkHome '<本机JDK路径>' -Tasks @(':recorder:assembleBundledDebug')
```

- App APK：`recorder/build/outputs/apk/bundled/debug/recorder-bundled-debug.apk`。
- App 仪器测试包：`recorder/build/outputs/apk/androidTest/bundled/debug/`。
- App 和识别库的仪器测试任务均使用 `connectedBundledDebugAndroidTest`；取消独立的 `tuning` 构建类型及包名后缀。
- Gradle 缓存放 `.gradle-user-home`，临时文件放 `.local-temp`，模拟器数据放 `build/avd`；项目位于 D 盘。
- 本机若继续遇到之前的 Maven TLS 问题，可在已有本地依赖仓库存在时给任务追加 `--offline --init-script build/local-dependency.init.gradle`。这是本机临时构建辅助，不提交依赖文件。

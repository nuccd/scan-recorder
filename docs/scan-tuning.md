# 扫码调优工作约定

## 分支与基线

- 调优分支：`codex/scan-tuning`。
- 对照提交：`5cde343`（0.4.1），创建分支时 `main` 也指向此提交。它是可回退基线，手持速度仍需实测。
- 每轮先记录假设，再改一个变量。相关验证通过后做一次本地 commit；实验结果写入提交说明，便于比较与回退。
- 验证后的改动再考虑合入 `main`。推送 GitHub 和合并按用户指示执行。
- Android Studio 本地配置、SDK 路径、APK、日志和测试数据不提交。

## 首轮实验顺序

以下是分别对比的实验，每轮与基线比较，避免把未经验证的参数叠加：

1. 仅将原生解码 `tryHarder` 关闭，观察能否降低单帧耗时，以及小条码成功率是否下降。
2. 仅将分析分辨率请求改为 1920×1080，检查设备实际选择及识别收益、耗时变化。
3. 若点击对焦后的等待仍明显，仅将阻帧从 300 ms 改为 200 ms，检查错误候选及相机调整状态。

首轮保持多帧一致性参数与 `minLineCount=2`。确认后保存、完整扫码框边界、多码阻止、重复开关及已有行号提示继续保留；同一帧两个引擎读到相同内容只算一次有效识别。不做 IMEI 校验或内容修正。

## 对比记录

- 使用同一台扫描手机，分别测试普通纸质条码、小条码、屏幕条码和二维码；保持同组的距离、倍率、光照及持握方式一致。
- 每组先做 10 次，5 秒未出现待确认窗口记为超时。记录成功次数、成功样本的耗时中位数和最慢耗时、超时次数、错误候选次数；识别耗时从完整码进入框内算到待确认窗口出现。
- 核对候选后取消，避免写入业务记录。再次测试同一码前移出扫描框，遵守已有重新触发规则。
- 同时记录提交号、机型、倍率、实际帧尺寸及诊断状态计数。`decodeMillis` 是双引擎到合并回调的处理耗时，不是纯 ML Kit 耗时，也不等于完整识别耗时。
- 原生日志目前只在首次命中时记录一次耗时，不能据此比较各引擎的平均耗时。需要这类比较时，先补充不含扫码原文的诊断。
- 构建继续使用 `scripts/build.ps1`；实验 APK、日志和截图保存在 D 盘项目的 `build/tuning/<实验编号>/`，由 Git 忽略。记录原文及用户截图不写入仓库。

每轮提交说明至少包含：改了哪个变量、为什么改、如何验证、观察到的收益或退化。速度变快但错误候选或超时增加时，需要保留两方面结果。
